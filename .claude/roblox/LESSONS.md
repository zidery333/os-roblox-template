# Lessons for every Roblox game

Every game's CLAUDE.md loads this file. Each line is a rule that came from a real mistake.

## How lessons are written

- **When:** a check fails for a reason that could happen again, a playtest shows a mistake, the person
  reports a bug, or they correct you.
- **What:** in the same turn as the fix, add one line: `- <the rule>. Why: <what goes wrong>.`
  Lines here never name a game or carry a date: each must make sense in any game.
- **Where:** only this game? The game's own `CLAUDE.md`, under "Lessons (this game only)". Any Roblox game?
  Here. How a model is built, how it should look and how its prompt is written? `/make-model`'s own
  `LESSONS.md`, or the game's `Model Lessons.md`. Picking the right Studio before any MCP call is in every
  game's own `CLAUDE.md`, so it isn't repeated here.
- **Keep it clean:** search this file first. If a rule already says it, make that rule sharper instead of
  adding a second. A rule a machine can catch becomes a check (a selene setting or a test), not a line here.
  After each build, move game rules that hold for every game up to here, merge repeats, and drop rules a
  check now catches. The aim is 80 rules or fewer. This file starts above that (about 110), because each
  rule is a distinct general one, so tidy before adding and never let it pass 120.
- **Checks that already replaced rules** (the starter kit carries them all, and `./check.sh` runs them):
  selene's `deprecated` lint with the kit's `roblox-game.yml` (old `wait`, `spawn`, `delay`, `tick`,
  `elapsedTime`); selene on `Tests` too (two tests with one name, an `assert` with no message); selene's
  Roblox standard library (`Vector3.yAxis:Cross(v)` fails: write `Vector3.new(0, 1, 0):Cross(v)`);
  `Tests/Source.spec.luau` (old calls like `:connect(`, `:Remove()`, `:GetMass()` and `BodyVelocity`, every
  remote named in `Code/Shared/Net.luau`, no top-level name declared twice in one file, no two files whose
  names differ only in capitals, every DataStore call inside a `pcall`, no emoji in `Code/`, no
  `.studio.luau` under `Code/`, no `MoveToFinished:Wait(`, no `Source = [[` (write `[=[ ]=]`), no `_G` in a
  file Lune runs); `check.sh --fix` runs stylua twice and stops `lune run` after 5 minutes;
  `Tests/run.luau` fails with no tests; and luau-lsp's type check with Roblox's types (a misspelled Config
  key, a method Roblox doesn't have on a typed value, a nil where a value is needed).

## Studio and the MCP

- Never use a method you haven't seen in the Roblox docs; unsure, look it up with the MCP's `rbx-docs-search` skill. Why: AI makes up methods, and the type check only catches them on a typed value, never on an `any`.
- After an MCP edit to the world or the UI, look at the tree or a screenshot to confirm it. Why: the MCP can make a second copy of a frame by mistake.
- `require` inside `execute_luau` gets its own copy of a module, kept between calls: never use it to read or set game state, and in a build script require `module:Clone()` (or search a module's `Source` text, since a clone has no parent for relative requires). A module can gain a relative require later, so a build script that needs several clones the whole `Shared` folder into ServerStorage, requires from the copy and destroys it at the end. Why: a module read 0 coins while the player had 6, after Rojo changed a module a later `require` handed back the old one, and a clone with a relative require errored.
- To call the game's own server functions in a playtest, put a temporary `Script` (its `Source` set) into ServerScriptService from a Server `execute_luau`; it runs in the game's own state, writes what it read to a workspace attribute and is gone when play stops. The client twin is a `LocalScript` put into PlayerGui from a Client call. That temporary Script is never destroyed while something it started still has a wait to run, and it has no `loadstring`: write each test as its own named command. A table crossing a BindableFunction is a copy without its metatable, so run methods inside the Script. A press the game's own screen module offers goes through that module; a remote fired straight from a test leaves the screen's own state open and holding everything waiting on it, so close it the way the game does and say so. Why: code run straight from `execute_luau` sees fresh module copies, not the game's state, and a thing it made never ticked; every `task.delay` it started died with it and left a round stuck, and a returned object failed with "attempt to call missing method"; a card stayed "busy" after a test fired the remote itself.
- Never wrap `execute_luau` edits in `ChangeHistoryService` recording, leave Lighting's `Technology` out of reads, and keep each call small (about 10 asset loads). Why: `FinishRecording(nil)` errored after the edit ran, reading `Technology` fails the whole read, and a 30-load call lost the connection.
- A Client `execute_luau` that changes `CurrentCamera.CameraType`, or fires a remote that makes the server set your character, gets the camera type put back when the call ends (a function a LocalScript runs for it too): do those by a real key press or button click, or start a camera move from the LocalScript's own thread; to turn the follow camera, set `CurrentCamera.CFrame` while it's Custom. Why: "The execute_luau changed camera type. Resetting..." undid the change.
- `script_grep` takes a Lua pattern, which has no `|`, and can leave out a script that has the word: search one word per call, and before calling a sync dropped read that script's `Source` with `execute_luau`. `insert_asset`'s `parentPath` can't take a name with a space: move inserted things yourself. Why: a five-word search found nothing and looked like Rojo had dropped, and imports landed in Workspace.
- When `list_roblox_studios` shows the window with `name: null` and calls say "Place is not open", read Studio's newest log for "Disconnected due to" (Mac: `~/Library/Logs/Roblox/`; Windows: `%LOCALAPPDATA%\Roblox\logs`, reached from WSL under `/mnt/c/`); wait a minute and list again, since Studio may reopen it by itself under a new studio id; only the person can reopen it otherwise, so finish the file work, keep Studio changes as a `.studio.luau` to paste later, and say what's left. Why: Roblox can shut a Team Create server down, and a second Studio started to reopen it stops at a login page.
- When `get_console_output` cuts a long playtest's head off ("TRUNCATED DUE TO LENGTH LIMIT"), read Studio's newest log: the game's own warnings and errors are its `[FLog::CreatorWarning]` and `[FLog::CreatorError]` lines. Why: setup lines filled the console and only the tail was left.
- No script can set `Players.MaxPlayers`, Game Settings > Avatar, or "Enable Studio Access to API Services": try them in `pcall`, list what failed, and hand those to the person; a game that's one player per server asks them to set Max Players to 1 before it's published. Why: the settings script failed on them, the saving test couldn't reach the DataStore, and with two players in one server, a world loaded from one player's save overwrote the other's.
- Importing models one after another: a chat holds `ModelImportLock` only for a moment between models, so wait for it inside one `execute_luau` loop that checks every half second, takes it, makes the change and lets go in the same call. Why: checking every 10 seconds never saw it free.

## Rojo

- If Studio reloaded, the Rojo plugin can sit on its "Sync changes" page (Accept / Abort) until a person clicks; a script can't. With nobody there, finish the file work and list the playtest as owed. Before a playtest, check the new code is in Studio's copy, down to the changed value; if files are missing, the Rojo plugin has dropped (a "WebSocket error 400" box): press Connect in its panel. Rojo syncs into Edit only: a tuning change means stop, check the value in Edit, start again. Every game's `default.project.json` sets `"servePlaceIds": [<its placeId>]` once the place has an id. Why: the page waited all night and nothing synced; Studio ran the old code after a playtest stopped, a playtest started a second too soon ran the old number, and a playtest already running keeps the old code; Rojo checks no place unless told, and synced into whichever Studio window was open.
- World changes made through the MCP live only in the open place until it's saved: keep them in a `.studio.luau` build script so the file and Studio match, and remind the person to save. A `.studio.luau` is run by pasting it into `execute_luau` in Edit, never by copying it under `Code/` for Rojo (not even as a renamed `.luau`), and never fetched from a local web server (Studio refuses localhost); one written offline is run before it's called done. A `.studio.luau` that reads or wraps a server module's field changes in the same change as that field: grep `Tests/` for the old name, since the type check reads only `Code/`. Why: a place went unsaved long after its world was built, deleting a copy under `Code/` killed Rojo's server until a person pressed Connect, and a script written blind pivoted on parts that weren't there; a renamed field left a watcher reading nil.
- Never make and then remove a folder under `Code/` while Rojo serves, for any reason (a throw-away type-check probe too): a probe is one file in a folder that already exists, deleted alone. Why: removing the folder crashed Rojo's file watcher, and Studio's plugin needs a Connect click to come back.
- To run only a new section of a big build script on what it already built, copy just the helper functions it calls, never the lines that make the model's folders, name its locals apart from the script's top-level ones (selene's shadowing warning fails `check.sh`), and read the tree back after. With Studio out of reach, run a build script's maths offline in Lune on a small table mock of instances (properties, children, a Model's pivot and bounding box): Lune's own Roblox instances can't take `implementProperty` for a property Roblox already lists. Why: the folder lines would have doubled every folder, and a pasted section failed lint 22 times; the real instances failed on reading `Position`.
- A scripted text edit (a Python `replace` between two markers) asserts each marker, the end one too, is found exactly once, the cut isn't empty, and the file's size after; a script that edits several files checks every file's markers before it writes any. An end marker that is a block's closing `end` includes its newline and indent, and after `check.sh --fix` a line written as one may be several, so a cut runs to a statement's real end. A scripted rename of a local finds it as a whole word and asserts how many it changed, never by a pattern with its punctuation (`(row,`), and it reads the result back, since a whole-word rename also hits table field names. Why: `s.index("return Hub")` matched a longer line, an empty cut put the new text between every character and pushed an 11 MB file into Studio, and half a change was left behind; stylua puts long calls' arguments on their own lines, nothing type-checks `Tests/`, and a missed use builds silently.

## Code and types

- The server decides money, damage, items and saves; a client script only asks, through a remote. Every test seam (a panel, a dummy, a switch) is Studio-only on the server too: its remotes are made only inside `RunService:IsStudio()`, and every test-only server function starts with its own `IsStudio()` check, its whole signature on one line. Why: a coin button in a LocalScript can be cheated; a seam with no check is a cheat in the live game, and stylua split a long signature out of the check's reach.
- A grace or window the server opens at a client's press opens again only after a gap since the last release; a right that runs out on a clock is checked again wherever it's acted on later, never only when it was given. A shortcut or side path keeps the main path's rules: a test-panel button that sets a value straight also runs what its events would, a "pick another" fallback keeps the first pick's exclusions, a new hook on an event goes into every setter of that event, and a sound tied to an event plays for every one, never only when its effect does. Something that happens between ticks adds to the tick's running sum, which the tick clears after using, never at its start. Why: a client toggling the press stayed inside the grace for good, and an expired right still worked in a later round; a test bar skipped a cost, a hook missed the panel's sets, and a quiet event made no sound.
- Anything a player keeps for a round (a colour, a slot, a home spot) is given by UserId when the round starts and stored, never read from their place in the member list. A thing a player owns, numbered from 1 per player, is found by owner and number, never the number alone; a per-player leave hook never reads another module's per-player state (hooks run in start order, and an earlier one may have cleared it): go by the thing itself (an `Owner` attribute). Why: someone leaving shifts everyone after them, and colours changed mid-round; another player's #1 matched too, and a leave hook read a list another hook had just cleared.
- Scaling a world up is never one multiply: player-sized pieces (gaps, doors, tiles) keep their size, anything charged per second costs more per route as routes grow, and a time or speed that wasn't scaled now races a distance that was. Shrinking back is the same list the other way. Run the build checks after and walk each "goes to X, then Y". Why: a 3x world put a head out of its band, made running reach an alarm, and had a walker give up mid-route.
- A server check on a key press works from its copy of the character, which trails the player's screen by about 0.2 s, and presses arrive bunched: allow a little more reach (the biggest size, for something that shrinks), try a press with nothing in reach once more 0.3 s later, and let presses through closer together than the client sends them. A server rule about a player's jumps and landings reads their height and the gap from their feet to the floor, never their up-down speed. Why: presses at the right spot were refused, fast presses counted half, and a held action stopped halfway; the server's copy of a jump read 0 rising speed most of the way up and bounced at touch-down, so "nearly still" missed most landings.
- Setting `player.Character` to another model makes Roblox destroy the old one about a frame later: to keep it, clone it first, set the copy up through the same function as a new one (`Clone()` drops `SetStateEnabled` and connections), put it in place, destroy the original yourself, and remember it by a number attribute. To replace Roblox's character sounds, a client script disables and destroys `RbxCharacterSounds` (Roblox puts it into PlayerScripts at every play start, and again if it arrives later) and removes the sounds it made in the HumanoidRootPart. Why: the old model was deleted, and copies didn't behave like the original; the old footsteps kept playing.
- A model worn as an Accessory welds its other parts to the Handle with a `Weld` whose `C0` is worked out from the template (`handle.CFrame:ToObjectSpace(part.CFrame)`), never a `WeldConstraint`; a check of anything worn measures every part's distance from the head, not only the joined attachments. A body from `Players:CreateHumanoidModelFromDescriptionAsync` arrives with Roblox's own `Animate` script, which never runs on a server-made body: load its `walk` and `idle` Animations on the body's Animator from the server and drop the script. Its `BodyColors` is named "Body Colors": find it by that name, and cast it. Why: a weld made outside the world takes its offset when it first enters it, after `AddAccessory` has moved the Handle, so sides hung hundreds of studs away; the body stood still, and the old-mover check fails any `"Body..."` string.
- A controller's stick also moves Roblox's own button selection (`GuiService.SelectedObject`): a screen where the stick does something else picks its buttons with the d-pad or bumpers and never sets the selection. A mouse drag works from `GetMouseLocation()` at the press and each move, never `InputObject.Delta`. Why: the selection wandered off the menu and A did nothing; `Delta` read (0, 0) on every move with the mouse free.
- Phone buttons stay out of Roblox's thumbstick area (the left 40% of the screen below its top third) and fire only on a clear tap (pressed and lifted on the button, quick, nearly still), never `Activated` alone; a PC has no such area, so a layout keeps out of it only on a touch screen (`PreferredInput`). A button in the bottom-right finds Roblox's jump button (`PlayerGui.TouchGui.TouchControlFrame.JumpButton`) and sits beside it, with a guessed box when it isn't found, since a PC Studio play window loads no PlayerModule. Why: a button by the left thumb fired by itself on a phone, and a PC hotbar sat off-centre for nothing.
- A Luau `if ... then f() else g()` expression keeps only the first value a call returns: call it in a plain `if` block. The type check can't follow some shapes: a value set inside `if not x then`, `map[k] = if v then v else nil`, a loop over an untyped table literal, `if ... then {} else {}` or `list or {}`, a table literal passed to a map-typed parameter (type the local, or pass it through a one-line helper), a loop over a typed record's keys (loop over a list of the names), a list of a big record passed as a smaller shape (map it first), a string local compared then set (read it into a fresh `local now: string` or a boolean first), a string-union result put in an untyped local, a value from `setmetatable` compared with nil (return early on `if not run then`), and a `string.gsub` callback typed `string?`. `pcall(f)` on a function that returns nothing needs `local ok: boolean, err: any = pcall(f)`. Fix the shape (a new or typed local, a plain `if`), never cast to `any` or add an ignore. Two client modules that need each other never `require` each other, even through a third: the lower one takes the other's functions, handed in by the start script. Why: `local cf, size = if m then m:GetBoundingBox() else ...` left `size` nil; these were most of the errors when the check was added; luau-lsp fails a require loop.
- Numbers that count down or add up drift: a zero text is returned before rounding (`math.ceil` of a tiny negative is -0, and `math.max(-0, 0)` is still -0), and a "crossed it this tick" check uses the same small slack on both sides. A switch made by crossing a line latches once crossed, until something else changes it. Why: timers read "-0s", an event fired on two ticks in a row, and a homing turn that switched back at every pass looped wide.
- With `StreamingEnabled`, client code that walks the world at start also listens to `DescendantAdded`, tries a model again as its parts arrive and as what it draws from arrives (a player attribute), and disconnects a thing's connections when it leaves; a model the client always needs is `ModelStreamingMode = Persistent`, one it changes whole is `Atomic`. Why: far parts arrive later, and a streamed-out instance comes back as the same instance with its old connections, so it was missed or watched twice.
- With no character (`CharacterAutoLoads` off) the server calls `player:AddReplicationFocus(part)` on a still part in the middle of the play area and keeps it across rebuilds (taking it off and putting it back in one frame warns "already exists"). Why: nothing made at runtime reached the screen.
- Client start-up never waits for ever: `WaitForChild` gets a time limit, warns once naming what's missing, then carries on, and a script that waits runs in its own `task.spawn`. Why: "Infinite yield" filled every log, and one missing label would stop every client script after it.
- A remote fired just before the server changes a value can arrive after that change has replicated: a screen that holds a number back reads the new total from the remote's own data. A server-to-client remote fired at join, before anything listens, is held for its first listener only: one client module owns it and keeps what it said, and every screen reads that module. Why: a prize showed in the bar before its reveal, and a second listener heard nothing.
- Anything that waits (a path, a tween, `task.wait`, a store read, a `task.delay` before an ending) can come back to a changed world: look the thing up again by its number, check the reason still holds, stop if it's gone, and ignore the same press until it's done. A watcher started from two places marks itself busy while it waits and checks after that it's still wanted. Each thread makes its own `Path`, and a chunked build that stops for a newer one first puts in or throws away the chunk it made. A tween's `Completed` still fires when its part is destroyed mid-tween, so test a "might hang" worry before fixing it. Why: a round's end rewarded a player whose state changed while it waited, a removed thing errored, two quick presses opened two of the same thing, and a model built twice; a shared path handed one walker another's route, and half-made pieces could be hit but never seen; a review listed three hangs from an old comment and none could happen.
- A check that waits for a move to finish asks the mover's own in-progress flag, never "its start time is still inside its failsafe window", and a client waiting to be moved hears it from a flag the server sets after the move, not from its root jumping. A queue that plays its first item at once marks every item it took as pending before playing any. Why: an action right after a move did nothing for 6 s, and a play re-queued the same items from inside itself.
- MessagingService allows 1 KB a message, (40 + 80 x servers) received a minute per topic, and 600 + 240 x players sent a minute per server: anything sent on a timer packs into as few messages as fit and caps its rate, with a test that works out the rate a minute. Why: a live feature sent up to 1,900 messages a minute to one topic.
- Measure the player's own character in the Client, and cast rays that find a spot from above everything, or from just above a thing at the floor parts only (`Include`, listing every part players stand on, not only the floor). A ray only sees parts in Workspace: a build script or server code that checks or lays out a model with rays parents it to Workspace first, in the same frame. To keep a thing a gap off walls, test every wall part's shape (`GetPartsInPart`, a probe grown by the gap, moved in till clear), never one ray out from its spot. A test teleport (`PivotTo`) goes to a spot such rays found clear, and `CFrame.lookAt(a, b)` never has `b` at `a`. Why: the Server's copy was a stud off, a ray that starts inside a part never hits it, and a high ray hit a roof instead of the floor; a ramp check on a model in ServerStorage found no floor, and a slanted wall or a rock beside a spot is nearer than the ray says; a teleport into a solid part drops the character through a thin floor, and a zero direction is NaN and kills the character.
- An invisible wall that stops players stands on the floor, with no gap under it as tall as a character (an R15 is about 6), and is taller than 2.4: an R15 walks up onto a solid part 2.2 tall without jumping. Why: players walked under a wall and up the steps behind it, and a 2-tall bench was stood on.
- `GetPartBoundsInRadius` and `GetPartBoundsInBox` test parts' bounding boxes, not their shapes: a check that something stays clear of a round part uses `GetPartsInPart` with a ball part the right size. `Raycast` sees through parts with `CanQuery` off, so a line-of-sight check works those out by maths. Why: a path check said most paths touched a hill whose cylinders' square boxes reached 30 studs past their sides, and a glow check said "clear" through a deep ledge.
- Find a part by name with a class check and its parent, never `FindFirstChild(name, true)`; children come in no set order, so a swatch of a model takes its named part's colour (its `Body_` part), never `FindFirstChildWhichIsA("BasePart")`'s; reach a child named like a property ("Name", "Size") with `FindFirstChild`, never a dot. Why: a joint with the same name was found instead, a trim part's white showed, and `slot.Name` is the slot's own name.
- Set `Motor6D.Transform` in `RunService.PreSimulation`; to check what's drawn, read parts in a `task.defer` from `PreRender`. A limb hanging from its hinge swings forward (to -Z) with a positive `CFrame.Angles(a, 0, 0)` Transform: work the sign out on a point under the hinge before writing it. A Humanoid lets a landing character dip 0.2 to 0.55 studs into the floor for a frame: a model riding an invisible collider is lifted back by that dip (raycast down, aim at where it'll be after the step), capped above 0.55. Why: set later it shows a frame late, a fix looked like it didn't work, and a swinging part went the wrong way; a ball showed inside the floor on every landing.
- Roblox deletes loose parts below `Workspace.FallenPartsDestroyHeight` (-500 unless set), and cuts any part side over 2048 studs down without a word: set the height in Edit for a low play area, and build long walls in pieces and read the sizes back. A `PointLight`'s `Range` stops at 60: a bigger room gets more lights, counted against the lights budget. Why: a character walking to a low floor lost its body, and players walked off a wall cut short; a bigger range is ignored and the room stays dark.
- `PathfindingService` ignores parts with `CanCollide` off (a `PathfindingModifier` on one too): a no-go zone is `CanCollide` on, `CanQuery` off, in a collision group that collides with nothing, and walkers share a group that doesn't collide with itself. Path points ramp smoothly up a step and over open edges: every walker the server moves (a low hip too) feels for steps with a short ray and jumps, high floors get walls or a set route, and a walker sent within reach R of something aims at most 0.7 x R out (1.41 times that at a corner), then walks straight at it. A wall walkers may break gets a `PathfindingModifier` with `PassThrough` and a `Label`, every path sets `Costs[label]` (`math.huge` goes round, 200 goes round when there's a gap and through when there isn't), and wall-breakers don't jump. Why: walkers cut through zones and bumped each other; walkers stalled at steps, dropped off decks, and stood just out of reach re-pathing for ever; without a cost on every agent all of them walk through, and jumping paths go over a low wall.
- Roblox's camera occlusion ignores invisible parts and parts with `CanQuery` off, so it never stops at a thing drawn client-side over invisible server boxes: each frame after the camera, pull the camera in where a line from its focus first meets the boxes, at once, and ease it back out. To pin a player's camera zoom (`CameraMinZoomDistance` = `CameraMaxZoomDistance` = d), lower the min first, then set the max, then the min. Anything drawn on the player's own character that must never block the camera is hidden by an exact test in a `BindToRenderStep` after the camera (the line from the camera to the head through its box, grown a little), checked by counting frames where a shown part sits on the line. Why: the camera went inside a big body, and a line grazing a moving body snapped it in and out; Roblox ignores a max under the current min, and a loose rule hid a worn part in every frame from behind.
- A solid anchored part the server moves by CFrame onto a player (a hit box as it turns) doesn't push them out: they stand stuck inside until it moves off. Something about to strike keeps still, or each client sets `CanCollide` off on its own copy of the boxes once its root is inside one and on again a few studs clear. Something the server moves while anchored (a player held or carried) is drawn on every client each frame from its carrier's drawn, smoothed model, in a `BindToRenderStep` just before the camera; a client-drawn thing riding another is moved after its carrier, in a second pass. A playtest checks it from a `BindToRenderStep` after the camera. Why: a character's physics runs on its owner's screen, and players stood inside a turning box until the grab landed; held players jumped 20 times a second on a phone, a rider read its carrier's last-frame hop, and an `execute_luau` read sees the server's spot and looks broken.
- Lune has no `Random`, so a `Logic/` module that rolls takes a number source (`rng: () -> number`, giving [0, 1)): the server hands in its own seeded `Random`'s `NextNumber`, the spec a small xorshift. selene fails a `"\u{00B7}"` escape (`bad_string_escape`): write a character outside ASCII as its UTF-8 bytes (`"\194\183"`). A pick that must match on every server (say, daily goals from the day and UserId) hashes its seed with a 32-bit mix, never a plain Park-Miller seed, and a test counts the spread over a month; a run of one pick in play is checked over the real seeds in a few lines of Lune before anything is called biased. Why: a module that calls `Random` can't run in a test; the lint fails the whole check; one goal in a short list never came up in a month, and a streak that looked lopsided was fair.
- Tell a real player from a test dummy by whether a member has a `Player`, never by the UserId's sign. Why: Studio's play-solo player is the signed-in account with its real UserId, so a sign test is right in one setup and wrong in the other.
- Tracking with `AnalyticsService` works only from a published game's server: each call is in `pcall`, skipped when `RunService:IsStudio()`, and what would have gone is printed behind a Studio-only switch left off. An onboarding funnel step counts every earlier step as done, so a step reached after a later one is flagged and never sent late; once-ever flags live in the save. Limits: 100 custom event names, 10 funnels, 5 currencies, 20 transaction types, 100 SKUs, breakdowns only through `CustomField01..03`. Why: sending steps as they came counted a player who left early as having finished.
- A text filled into a sentence brings its own little word ("grew into {stage}" with "a Juvenile" and "an Adult" in the string, never "a {stage}"), and a count of 1 gets its own text. Why: a label read "a Adult" and "1 eggs".

## Plans and tests

- A step's build reads its own block in the game's design files as well as the plan's summary, and checks every count in its Done-when against what earlier steps really built, fitting the test to the build and saying so. A `Plan.md` edit changes only the step's own lines, never the text up to the next heading. Why: a step nearly left out a setting, an old "always 12" was written before 60 existed, and a status write deleted another chat's new step.
- Any rule about two or more players (who can rescue, whose colour, who carries what, what a leaver takes with them) gets a test on a pure function plus a scripted server check with a second player or the game's test dummy. Why: two-player bugs, one deleting an item from a friend, all passed every solo playtest.
- A test that fires one of the game's remotes sends its arguments the way the client does (an id as a string where the client sends one: the server's type check drops anything else without a word), and waits out the remote's rate limit between two presses, the screen's own presses too. ## Saving

- Wrap every DataStore call in `pcall` and handle the failure; treat an error as not worth retrying ("API Services", "publish") only in Studio, and live, retry with waits. Until "Enable Studio Access to API Services" is on, saving in Studio uses a memory store and says so once, and a real save test waits for the person to turn it on. Why: an unguarded call killed a first run, live outages also say "502: API Services", and no script can turn API access on.
- A save after every change a remote makes is held to one per player every few seconds, the last change saved when the gap ends. Each ProfileStore `Profile:Save()` is one `UpdateAsync`, and a server may write 60 + 10 a player a minute. Why: three remotes that each saved at once let one player spend the whole server's budget.
- Build the save from its parts, each in `pcall`, and guard each load hook and each item of a saved list: on a failure warn, keep what was saved for that part, mark the save not writable, and kick outside Studio. Why: one broken part would end autosave for the server's life, one bad piece stopped the load and nothing saved all session, and items after a broken one were wiped by the next autosave.
- Never write over a newer save: store a `savedAt`, refuse a write when the stored one is newer (`UpdateAsync`), and on join wait for that player's last leave save to finish. Why: a fast leave and rejoin, or two servers, loaded an old save and wrote it over the new one.
- On server shutdown, `game:BindToClose` saves every player still in and waits for those saves. Only the save module drops a player's data, after its last snapshot on leave. Why: without it a closing server loses everything since the last autosave; another module cleared its part on `PlayerRemoving` and the leave save read an empty one.
- Never trust saved data: a missing, text or negative version is floored and clamped, tables already there are kept, numbers are checked for NaN and `math.huge` and capped above and below, lists lose doubles, places are checked against the play area, and levels are held to what unlocks them. Why: `math.max(NaN, 0)`, `math.min` and `math.clamp` hand NaN straight back, `math.floor(math.huge)` is `math.huge`, a negative version looped for ever, and a bad version rebuilt the wallet empty and saved it.
- Save what a thing's state is ("finished") instead of working it out from its model. Gains made while a save is loading are added to it, and a queued save says "saved" only after its write worked. Why: a model that gained pieces made every finished one load half built; coins earned in the first seconds vanished, and a failed write was logged as saved.
- ProfileStore has no `IsMock`: its test store is `ProfileStore.DataStoreState ~= "Access"`, kept in memory and gone when the playtest stops (a real leave and rejoin needs Studio's API access on), and its exported types leave out `StartSessionAsync`'s documented `Cancel`, so read the module through your own small types. A download question names the licence from the repo's own LICENSE file, never from memory. Why: a note named the wrong flag and the wrong licence.
